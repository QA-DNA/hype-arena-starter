# Text -> facts (subject, attribute, value): ranked techniques for Hype or Truth

Status legend: [FACT] = from a primary source / documented; [EST] = my estimate from general experience, NOT measured on this data or this CPU. Benchmark it in the first hour. Web search returned no usable CPU-throughput tables (only GLiNER2 205M: ~130-210 ms/text on CPU, per its paper), so all throughput numbers below are [EST].
Note: the researcher.md instruction file given in the brief does not exist at that path; I proceeded with the brief's own requirements.

## 0. Diagnosis (what actually limits us)
Judge: gold facts 92% vs our facts 87%. Parser P=0.91, R=0.69. So the gap is RECALL (booleans 0.20, names 0.49, dates 0.64), not precision. Practice facts: 1,897 rows, 1.3 facts/row; kinds: quantity 1028, money 268, duration 229, name 209, percent 201, boolean 174, date 165, version 128. Implications:
- Values of numeric kinds (quantity/money/percent/duration/version/date) are regular expressions territory: contracts/value-forms.md is a deterministic grammar. Keep rules for VALUE spans (high precision, ~complete). Learning is needed only for (a) value -> attribute assignment, (b) names, (c) booleans, (d) subject. Do not spend model capacity on number spans.
- Bottleneck is therefore a classification problem over (candidate value span, sentence context) -> attribute, not open-ended NER. Closed-world candidate generation + learned scoring beats free sequence tagging at 1.9k sentences.
- For the judge, a fact only has to be good enough to look up a timeline: (subject, attribute) key + value comparable. A fact with right key and wrong value is useful (judge can say false); a fact with wrong key is harmful. So optimise key accuracy and recall of keys, then value; emit partial facts (key + candidate values) with confidence, let GBM use the match score as a feature.

## Ranking
1. Candidate-ranking pipeline: rule value spans + lexicon-constrained (subject, attribute) scorer (GBM/LR over rich features incl. static embeddings) + discourse subject state  [BEST VALUE/EFFORT]
2. Linear-chain CRF (sklearn-crfsuite) for name/boolean/entity spans and attribute-slot tagging, features from lexicon + context
3. Small fine-tuned encoder (MiniLM-L6/L12 or DeBERTa-v3-xsmall/small, ONNX int8) as a span/slot classifier, trained on gold + LLM-synthesised paraphrases
4. GLiNER-style zero/few-shot span model (fine-tuned small checkpoint) - only as a name/entity-span fallback; weakest fit.
Not recommended: BiLSTM-CRF, spaCy NER from scratch, generic RE/KBP systems, template mining (already failed).

## 1. Candidate generation + constrained scoring (extend current parser)
What: For each sentence, (i) extract all value spans by the grammar (already ~complete for numbers), (ii) generate candidate subjects (lexicon aliases in sentence + carried-over subject(s)), (iii) for every (value, subject, attribute in lexicon[subject] with kind == value.kind) build a candidate fact, (iv) score with a discriminative model, (v) pick top candidates by a threshold and one-fact-per-value constraint. This is the standard "candidate generation + ranking" design of TAC-KBP slot-filling systems [FACT: Surdeanu, "Overview of the TAC2010 KBP Slot Filling", and Stanford's KBP 2013 system, Angeli et al. 2014 - pipelines of candidate generation + classifier beat pure sequence labelling in small-data regimes; I cite from memory, verify before quoting].
Why fits: kind compatibility from the lexicon (514 subject-attribute pairs) prunes candidates to typically 1-5 per value; the classifier only discriminates among a handful. This is constrained decoding for free, with no CRF needed. Joint decoding = per-sentence assignment: each value to at most one attribute, each (subject,attribute) at most once per sentence (Hungarian / greedy by score).
Needs: sklearn (already), numpy. No new heavy deps.
Runtime: microseconds-ms per candidate; 20k rows x ~10 candidates in <1 min on 1 core. Image: +0 MB.
Features (pairwise, value-centred): bag of words/bigrams in windows left 1-3 / right 1-3 tokens of the value (keeps position), words between value and attribute-cue lexicon, unit/noun after number (e.g. "engineers" -> team_size), attribute-name cue words from lexicon alias lists (fuzzy/stem match), verb lemma ahead (launched, costs, hired), sentence TF-IDF -> attribute logistic score (you already have; use as feature, not final), kind, value magnitude bucket, whether another value of same kind exists in sentence (ordering feature), whether subject was explicit vs carried, subject-attribute prior (frequency in train), relative position of subject mention vs value. Train GBM or LR as binary "this candidate is gold" on the 1.9k rows (about 2.5k positives; negatives are the other candidates; cheap).
Expected gain [EST]: biggest single lever on recall for numeric kinds; today's classifier is sentence-level (one attribute per sentence), so multi-fact sentences (20% of rows have >=2 facts; 373+) lose recall. Expect recall 0.69 -> 0.75-0.80 mostly from this plus subject handling; precision ~flat. I have no ablation on your data - run: oracle-attribute test (give parser gold attribute, see how many points of recall return) to bound the gain before building.
Pitfalls: label leakage via carried subject (build features without gold subject); duplicate facts across adjacent rows; train/eval split must be by page/date block, not random rows, else adjacent-row carry-over features overstate.

### 1a. Missing subjects (33% of rows)
Techniques, in order of cost:
- Entity-state tracking (centering-style salience): per page/doc keep a stack of last explicit subjects with recency; a pronoun/"its/the platform/the company/he" or subject-less sentence takes the most recent subject whose attribute set accepts the sentence's attribute+kind. Choose subject JOINTLY with attribute: score (subject, attribute) pairs, prior = recency decay, likelihood = attribute classifier; this resolves "subject-less" by compatibility rather than recency alone. Reference idea: Grosz, Joshi, Weinstein 1995 "Centering" (Computational Linguistics 21(2)); entity-grid coherence, Barzilay & Lapata 2008. Practical: learn P(same subject as previous row | features) with a GBM using: starts with pronoun, type of cue words (Its/His/The platform), date gap, previous row's subject type (person vs product), and compatibility score. Pronoun gender/animacy gives a free person/product filter (he/she -> person subjects; its/the platform -> product).
- Type-head nouns: "the plan", "the team", "the platform", "the app" -> map to lexicon subject types.
- Abstain on subject when top two compatible subjects tie: emit fact with subject=None + candidate list; judge then looks up both and takes the max/min support as a feature (soft). This is cheap and converts an error into an uncertainty feature.
Check first: how are rows ordered? If ids/dates group a page's rows consecutively (p-1..p-7 above are clearly one page), carry-over by adjacency is valid at test time too; verify real input has the same ordering (no 'page' column known).

### 1b. Booleans/negation (recall 0.20)
Booleans are 8% of facts; they are attribute-led, not value-led: the "value" is the polarity of a predicate ("has", "supports", "is open source", "does not offer"). Recipe: for each (subject, boolean attribute) in the lexicon, a binary relevance classifier "sentence asserts this attribute" (cue lexicon from aliases + TF-IDF LR) and a polarity classifier (negation cues: not, no, never, without, "n't", "lacks", "dropped", "ended", "discontinued", "no longer"; plus scope heuristic: negation within same clause up to 4 tokens before cue). Note referee says negation makes values unreadable but 'yes/no' is its own form: read contracts/value-forms.md "Yes or no" for the exact cue list and mirror it in the parser. Low recall is likely because the current parser needs a value token; booleans need attribute-driven candidates. Add them as candidates for every boolean attribute of every subject-in-scope and let the scorer decide.
Pitfall: false-booleans are probably where the lies hide ("Hooly now offers X" vs a timeline saying it ended) so recall here is valuable for the judge, but precision error flips truth label; keep a confidence output and let GBM weigh it.

### 1c. Names (recall 0.49) and dates
- Names are values of attributes like reliability_lead, previous_employer (person/org names). Candidate generation: capitalised token runs not at sentence start (or at start but not a stop-word), plus gazetteer of every name seen in practice facts AND in the lexicon (subjects/aliases) AND in all 20k rows' capitalised n-grams with frequency >=2 (unsupervised gazetteer from the test inputs themselves is legal - it is the dataset, not outside knowledge). Then the same candidate scorer with features: left-context words ("answers to", "led by", "joined from", "previously at"), is_known_person, is_known_org, appears-as-subject-elsewhere. Treat the name as unknown-to-lexicon; for the judge only string equality is needed.
- Dates at different precision: do not normalise to day; keep (year), (year-month), (year-month-day) with precision tag; "today/from today/this week/last month/in Q3" resolve against the row's date column: today->row date, yesterday, "last month" -> month-1 etc., "since X", "next quarter". Compare to timeline with precision-aware equality (equal at the coarsest common precision). Cheap, deterministic, likely +recall on dates 0.64.
Expected gain [EST]: names 0.49 -> ~0.65, dates 0.64 -> ~0.80 via these, as the failure is candidate generation, not scoring. Unverified.

### 1d. Abstention
Confidence = calibrated candidate probability (isotonic/Platt on held-out folds, scikit CalibratedClassifierCV). Emit top-1 fact if p>=t_hi; emit as "weak" feature if t_lo<=p<t_hi; else nothing. Pass p and the margin to the judge GBM, not a hard decision. Reason: the judge gets information from "the parser is unsure"; log-loss gains come from calibration. Use out-of-fold parser outputs to train the judge (the judge currently trained on gold facts or in-sample parser output would be over-confident - important: train the judge on parser predictions generated out-of-fold so it learns the parser's real error profile; this alone may recover part of the 92 -> 87 gap).

## 2. Linear-chain CRF (sklearn-crfsuite / python-crfsuite)
What: Lafferty, McCallum, Pereira, "Conditional Random Fields", ICML 2001 (the model); CRFsuite by Okazaki 2007 (the implementation, L-BFGS/ L1+L2). BIO tagging with labels like B-ATTR_x? Better: tag only NON-numeric slots: B/I-NAME_attr, B/I-SUBJ, BOOL_POS/BOOL_NEG cues, and attribute-cue spans; numeric values pre-tagged by rules as features.
Why: Works with hundreds to a few thousand sentences, trains in seconds, deterministic, tiny, definitely not an LLM. Feature engineering over lexicon matches, shape, gazetteer, window, previous tag. Sequence constraint helps names/phrases boundaries ("Nimbus Cloud") and cue-span extents.
Needs: python-crfsuite (C extension, ~1 MB wheel; builds for linux 3.13? check wheel availability; fallback pip install from sdist needs compiler in the Docker build stage, fine) + sklearn-crfsuite (pure python).
Runtime [EST, widely reported order of magnitude]: tens of thousands of tokens per second per core; 20k rows x 25 tokens = 500k tokens -> well under 1 minute. Image +few MB.
Evidence: CRFs remain the strong baseline for NER with tiny data (CoNLL-2003 ~89 F1 with feature engineering, Finkel/Manning-era systems; Lample et al. 2016 "Neural Architectures for NER" arXiv:1603.01360 BiLSTM-CRF 90.9 F1 but with 200k tokens of training and pretrained embeddings). With 1.9k sentences x ~20 tokens = 38k tokens and a closed label set, CRF with good features should match BiLSTM-CRF; neural nets only win with pretrained embeddings or lots of data.
Expected gain [EST]: +0.05-0.10 absolute recall on names and boolean cue spans when used as an extra candidate generator for module 1. As a replacement for module 1's scorer: no, worse (can't pair value with attribute globally).
Pitfalls: label sparsity (62 subjects x many attributes) - collapse labels to coarse roles (SUBJECT, NAME_VALUE, BOOL_CUE, NEG, DATE_REL) and resolve the attribute afterwards with module 1; otherwise CRF memorises. Need silver token-level labels: gold form gives values and subjects but not char offsets; align by string search (names and subject aliases are literal in the text - checkable; some values like Holdan appear verbatim). Measure alignment coverage first (maybe ~90%).
BiLSTM-CRF: needs torch (~200 MB CPU wheel) and gives no gain at 38k tokens without pretrained vectors; skip. spaCy NER from scratch: spaCy's tok2vec NER on <2k sentences is typically poorer than CRF; spaCy useful only for tokenization/POS (en_core_web_sm ~12 MB, ~10k words/s per core [EST]) which feeds features (verb lemma, dependency head of the number - nsubj/dobj gives value-to-predicate links). Risk: spaCy wheels for Python 3.13 / pydantic fine in 2025+; check offline model install at build time.

## 3. Small fine-tuned encoder (MiniLM / DeBERTa-v3-small, ONNX int8)
What: Token or span classification fine-tune of a pretrained transformer. MiniLM (Wang et al. 2020, arXiv:2002.10957): L6-H384 ~22M params (all-MiniLM-L6-v2 90 MB fp32, ~23 MB int8), L12-H384 33M; DeBERTa-v3-small 44M backbone + 98M embedding (~140M total, ~570 MB fp32) and xsmall 22M backbone + 48M embedding (~70M, ~280 MB); DistilBERT 66M (~265 MB). [FACT: HF model cards for params; sizes arithmetic]. Use it as a (value-in-context, candidate attribute) pair classifier: input "[CLS] sentence with value marked <v>...</v> [SEP] subject: attribute-description", binary or multi-class over lexicon attributes. This is the cross-encoder / entity-marker relation-classification setup (Zhou & Chen 2021 "An Improved Baseline for Sentence-level RE" arXiv:2102.01373; Baldini Soares et al. 2019 "Matching the Blanks" typed markers) - gives the encoder what it needs with the closed-world pruning of module 1.
Why: Semantic generalisation over LLM-written paraphrase ("the crew grows to 4" vs "team size") that bag-of-words misses. This is where the unexplained recall (33% unattributable) might be.
Needs: torch CPU (build time only), optimum + onnxruntime (onnxruntime CPU wheel ~15-20 MB manifold; runtime only needs onnxruntime + tokenizers (~3 MB) + numpy). Model on disk 25-100 MB int8. Image total <1 GB comfortably (3 GiB limit not a concern).
Runtime [EST, no measured table found]: MiniLM-L6 int8 on ONNX Runtime, seq len 48, batch 32, 2 threads: roughly 200-500 sequences/s; 20k rows x ~10 candidate pairs = 200k pairs -> 7-17 min worst case. Too slow if scoring ALL pairs; fix by (a) pruning with module 1 to top-3 candidates per value (60k pairs ~2-5 min), (b) encode sentence once with candidate markers on values only and classify all values in one pass (token-classification on value markers: 20k passes ~1-2 min). Use token-level formulation to stay safe. DeBERTa-v3-small is 3-4x slower than MiniLM-L6 and ONNX int8 export of DeBERTa-v3 has had accuracy/export quirks - prefer MiniLM-L12 or distilroberta if you need more capacity. Measure on the team's machine before committing (1 hour).
Training: 2 CPUs not needed - train on a laptop/Colab-free GPU/ any dev machine at build time (allowed). 1.9k rows + LLM synthetic data (Qwen2.5-72B/DeepSeek-V3.1 paraphrase each gold fact in 5-10 styles with gold labels preserved; 20-50k rows) is the real data lever. Evidence that synthetic LLM data helps small models: Wang et al. 2021 "Towards Zero-Label Language Learning" arXiv:2109.09193; GPT3Mix; for IE "LLM-generated training data for NER" (e.g., Ye et al. 2022 ZeroGen arXiv:2202.07922) typically reaches 80-95% of gold-data performance and mixing with gold gives +2-6 F1 [EST range from those papers; no guarantee on LLM-style target text, but here the target text IS LLM-written, so domain match is unusually good].
Expected gain [EST]: +0.05-0.10 recall vs module 1 alone if synthetic data covers the target style; risk of overfit to synthetic artefacts. Highest variance option; needs the 10-hour budget mostly for data generation + validation.
Rule risk ('may NOT be an LLM at run time'): the rule text, as relayed, targets LLM use at run time; a 22-100M-parameter encoder fine-tuned for classification is a "model", not an LLM by the field's usage (BERT-class models are called pre-trained language models; the term LLM today means generative models of billions of parameters). It is INFERENCE that organisers would treat it that way; there is no established fact about their ruling. Risk is real but moderate: a MiniLM (22M) is far from LLM scale, while a rule-checker could in principle object to "pretrained language model". Mitigation: ask organisers in writing (Discord/mail) NOW with the exact model and size; keep module 1+2 as a fallback that already works without any pretrained transformer (classical models: CRF, linear, GBM, TF-IDF are clearly safe; static word vectors (fastText/GloVe) are pretrained but non-generative and low-risk, though GloVe 300d is 1 GB - use only a pruned vocabulary or train word2vec on the 20k rows themselves for a few MB). Gain/risk call: only adopt if module 1 plateaus and organisers confirm.

## 4. GLiNER-style span model
What: Zaratiana et al., "GLiNER: Generalist Model for NER using Bidirectional Transformer", NAACL 2024, arXiv:2311.08526. Encodes label prompts and text together, scores spans against label embeddings. Sizes ~50M (small, DeBERTa-v3-small-based... model-card dependent), 90M (medium), 0.3B (large) [from search summary; verify]. Fine-tune with the `gliner` package (needs torch).
Why it ranks last: (a) numbers/dates/units are rule-handled already; the genuine gap is names/booleans/subjects, which have simple capitalisation/cue structure; (b) zero-shot labels like "previous employer" are relation-ish, and GLiNER predicts entity spans, not relation to a subject, so you still need module 1's pairing; (c) gliner torch dependency pulls ~1 GB in the image if not exported to ONNX (gliner supports ONNX export); (d) same LLM-rule ambiguity as option 3 with more params; (e) CPU speed reported only for GLiNER2 (205M): ~130-210 ms per text on CPU -> 20k rows = 45-70 min on one thread, i.e. over budget unless quantised/batched. Use only if you want entity-type features ("is this span a person/org/product") - there a 50M GLiNER with labels person/organization/product can add a feature at +0.0x; likely not worth it vs a gazetteer from the data itself.

## What would NOT help (be critical)
- Template/skeleton mining: already shown to fail (6% repeat).
- BiLSTM-CRF / spaCy from scratch on 1.9k rows: no gain over CRF+features, adds torch/pydantic weight.
- Dense open IE or generic RE (OpenIE, REBEL, TAC-KBP systems): wrong schema; closed lexicon is a stronger prior than any of them.
- Learning number extraction: a bug-for-bug grammar already exists; any learned span extractor will be worse than regex on a deterministic grammar (and the referee reads the same grammar for Task 2).
- Larger pretrained models "just in case": risk under the LLM rule and 30-min budget with no evidence they help closed-world pairing.
- Optimising F1 of parser in isolation: judge cares about calibrated, key-correct facts; precision 0.91 is fine, recall of the right (subject, attribute) key is what moves accuracy toward 92%.
- Tuning on random row splits: adjacent-row leakage overstates everything.

## Concrete 10-hour plan
1. (1h) Oracle ablations on practice: gold-attribute, gold-subject, gold-value-span substitutions into the parser to see which component costs the 5 judge points. Decide priorities from that, not from this note.
2. (3h) Module 1: value-centred candidate scorer, joint subject+attribute with discourse state, soft-subject output, date relative resolution, boolean attribute-led candidates. Page-block CV, calibration.
3. (1h) Out-of-fold parser outputs -> retrain judge on them. (cheap, likely largest judge-side gain)
4. (2h) CRF for names/bool cues as extra candidate generator; gazetteer built from all 20k inputs.
5. (1-2h, parallel by teammate) LLM synthetic paraphrases of gold forms (balanced across kinds/attributes, with relative-date and subject-less variants) to enlarge training for module 1 (works with classical models too: bag-of-ngrams scorer benefits directly).
6. (optional, only if organiser confirms) MiniLM-L6/L12 int8 token classifier on value markers; compare against module 1 on page-block holdout; ship only if +>=2 pts judge accuracy.
7. Always: time the full 20k-row run in the 2 CPU / 6 GiB container; budget must leave >=2x headroom.
