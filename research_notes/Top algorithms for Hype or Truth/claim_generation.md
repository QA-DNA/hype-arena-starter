# Claim generation (Task 2): 1,000 novel, true, referee-compliant claims

Sources read first: contracts/README.md, claim-forms.md, value-forms.md, entry.schema.json, examples/entry good+bad, scripts/check_output.py, data/lexicon.json, data/practice.csv (1,897 rows, dates 2025-10-07..2026-10-28).
Note: the instructed skill file `.../deep-research/references/researcher.md` does not exist on this machine; I proceeded from the task text. No web research was needed: the referee is fully specified by the contracts, so the "citations" are mostly design reasoning (marked) plus classic references for the techniques.

## 0. Key facts that shape everything (measured on practice)

- Rows: 1581 true / 277 false / 39 unsure. Lies are mostly STALE or temporal values (202 of 353 gold-form facts in false rows equal a value that a true row states for the same key; 151 are novel values). Caveat: 373 rows state 2+ facts and the label is per row, so a "false row" fact may itself be true. Do not treat a value seen in a false row as false; treat it as weak evidence.
- 514 (subject, attribute) keys; 252 change value at least once (true rows), 147 are stable with >=2 agreeing true rows, 75 have a single observation. Most late-year coverage: 215 keys last observed in Oct 2026, 83 in Sep. So the as-of value (29 Oct 2026) is usually the LAST observed value, but a minority of keys were last seen months ago and may have changed unseen.
- Event dates themselves change (Cloud Next 2026: 2026-06 -> 06-02 -> 06-09; Maps Day 06-09 -> 06-23; Sustainability Report published 08-25 -> 09-08; Android 17 stable_release 09-08 -> 09-22; I/O 2026 date row dated 2026-03-24 says plain "2026"). at_event and date-compare must use the FINAL event date and only events whose date fact has stopped moving. Pages announce future dates ahead of time (a Jan page states a June date), so a page's date is NOT the date the value holds.
- Aliases in lexicon: `Hooly` = {Hooly AI, Hooly Inc.}; many one-word aliases (Search, Maps, Photos, Chrome, Android, Gemini, Translate, Vault, Jules, Workspace plan, "Hooly's board", "Hooly's Q1 results"). The check_output.py originality test is: lowercase, whitespace-collapse, strip trailing `.!? ` and compare to practice texts. The real judge uses all ~20k input rows, so check against universe.csv, not just practice.

## 1. Ranked techniques

### Rank 1: Truth-discovery fact base with calibrated P(true on 29 Oct) and a selection threshold
What: build, per key (subject, attribute), a dated observation list from (a) gold forms on practice rows, (b) parser output on unlabelled rows; estimate the current value and P(value == truth at 29 Oct 2026); only keep claims with P above a cutoff; confidence = calibrated P clipped to [0.5, 1].
Citation: truth discovery over conflicting sources, TruthFinder (Yin, Han, Yu, KDD 2008, "Truth discovery with multiple conflicting information providers on the web"); survey Li et al., "A survey on truth discovery", SIGKDD Explorations 2015; Dawid-Skene 1979 for per-source error rates. Applying them to dated rows is design reasoning.
Why it fits: 14.6% of rows lie, parser precision on unlabelled rows is ~0.91, values drift; this is the dominant error source. A single wrong claim wastes a slot AND is judged for truth.
Needs: parsed (key, date, value, row_conf) tuples; the practice labels as calibration set. Runtime: seconds.
Expected gain: the difference between ~85% and ~97% true claims; largest lever in the project.
Recipe:
1. Observation weight w_o = log(p/(1-p)) with p = row trust: labelled-true practice row 0.97; labelled-false row 0 (drop, or use its other facts only if the row has one fact); unlabelled row = judge P(true) x parser precision (0.91), capped 0.9. Source-level lie rate prior 0.15.
2. Group observations by key and by canonical value (use exact normalized value: unit-converted, dates at stated precision). Separate "same value, different precision" (2026-06 vs 2026-06-02 are different values; do not merge).
3. Recency/changepoint: sort by date; current value = value of the latest cluster that has total weight >= 2 observations OR 1 observation with trust >= 0.95. Discard a lone latest observation that contradicts two earlier agreeing ones unless trust is high (it is the typical lie: 202 stale/temporal lies show a lone row differing).
4. P(true now) = sigmoid(sum of weights of current-value observations since the last change - sum of weights of conflicting later observations) x freshness factor f = exp(-age_days / tau_key), tau_key estimated as the key's mean time between changes (keys with 0 changes in 6+ months: tau large). Keys changed >=3 times or last seen >120 days ago: P multiplied by 0.7 or dropped.
5. Calibrate on practice: hold out the last observation per key as pseudo "as-of" truth with labels, fit a 2-parameter logistic of P vs features (n_agree, n_conflict, age, change_rate, source = gold/parsed). Report reliability bins; choose confidence = calibrated P.
6. Select claims with P >= 0.93 (see section 5 for margin by type); the 1000 slots are large relative to the candidate supply only for facts, so threshold, not quota, decides.
Pitfalls: counting the same sentence repeated across pages as independent corroboration (dedupe near-identical text per key, count distinct dates >=7 days apart); using parsed rows to confirm parsed rows (correlated errors from the same parser: weight them 0.5); boolean values where "not" is mis-parsed (exclude booleans unless gold-form or 3+ agreeing).
What would NOT help: LLM scoring of truth at run time (forbidden); a bigger model for the parser at this stage (extra 1-2% parse accuracy matters far less than agreement filtering); training a classifier on 1.9k rows with text features (overfits; the agreement features carry the signal).

### Rank 2: Type-specific candidate constructors on the timelines + a self-written referee (round-trip validator) gating every output
What: for each claim type, enumerate candidates from the timelines with a safety margin, realise text from a small controlled grammar that is a strict subset of the referee's phrase lists, then re-parse the text with an independent implementation of the referee rules and require round-trip equality with the form. Drop anything that fails.
Citation: controlled-language data-to-text is the classic template approach (Reiter & Dale, "Building Natural Language Generation Systems", CUP 2000; Gatt & Krahmer, JAIR 2018, "Survey of the State of the Art in NLG"). Claim types mirror TabFact (Chen et al., ICLR 2020) logical forms (count/compare/superlative/aggregation) and LogicNLG (Chen et al., ACL 2020); FEVEROUS (Aly et al., FEVER 2021) claim types. Those datasets use crowd workers or neural models for text and are NOT applicable offline; what transfers is the logical-form typology and the idea of generating from verified forms. Round-trip validation is design reasoning.
Why it fits: the referee is deterministic, regex-like and strict (section 3). A grammar that emits only fixed templates can be proven compliant by tests; "invalid claims still occupy slots".
Needs: lexicon.json, the contracts, a value writer per kind, 5 type constructors. Runtime: milliseconds per claim; whole pipeline well under 1 min. Build: ~3 h for constructors + validator.
Recipe (per type):
- fact: key with current-value P >= cutoff. Templates by (kind, attribute class) written once by hand for the ~300 attributes via an attribute-to-verb-phrase table (see 3.3); fallback generic template "{S}'s {attr words}: {value}." avoided (see pitfalls).
- compare: pairs of keys with the same attribute (70 shared numeric attributes) or same kind and convertible unit. Compute interval of each value on 29 Oct (current value +- change risk). Emit gt/lt only if the relative gap is >= 15% or the values differ in rank across ALL current-cluster observations; eq only if equal exact values in >=3 observations each. Dates: gt/lt only for events with final dates (dates differ >= 1 day), eq rare. Same-currency+period for money. Text states NO number (section 3).
- change: for key with an observed value sequence v1..vk (cluster-level, after step 3 of Rank 1) emit pairs (v_i, v_j), i<j, v_i != v_j. The referee only needs "held from, and at a later date to" so you may choose NON-ADJACENT pairs and the two best-corroborated clusters. Ordering: from earlier cluster, to later cluster; add up/down only for amounts (not dates, names, booleans) and only when direction is certain. A lone lie in the middle cannot hurt if you pick the two best-supported clusters. Risk: a->b->a (revert): `from a to b` is true and `from b to a` true; but beware that a mis-clustered lie looks like a revert; require each side's cluster weight >= 2.
- at_event: for event E with final date d (date fact stable: last 2+ observations agree at day precision) and key K with observations bracketing d: latest obs <= d and next obs after d agree (or the key is stable overall). Prefer facts about the event itself (attendees, ticket_price, sponsors, talks) only when the subject differs from E; the referee resolves value on E's date for the subject, so an event's own attribute ("Hooly I/O 2026 attendees at Hooly I/O 2026") is awkward; use other subjects.
- relation: link key (subject, link attribute) with name value whose target is a lexicon subject (40 of 209 name facts; 28 targets have `joined`). Need the target's attribute value and the link period (first/last date link named target): true if the target's value (e.g. joined date) is constant. `joined` dates are constant facts and the safest. Also `venue`->capacity, `chair`->independent_director, `lead`->joined.
Pitfalls: see section 3 (the gotcha list); main ones: one value per sentence, no time words, no month names, names inside bigger names, booleans need attribute words and polarity.
What would NOT help: LLM paraphrase to increase surface variety (not allowed at run time, and any paraphrase outside the phrase lists makes the claim invalid); neural/pretrained data-to-text (ToTTo, Parikh et al. EMNLP 2020) - it hallucinates and breaks exact phrase forms; fancy morphology.

### Rank 3: Submodular / quota selection for diversity and originality
What: choose the final 1,000 from the validated, high-P pool by greedy maximisation of coverage (+ P) with type quotas and per-subject/per-attribute caps.
Citation: monotone submodular maximisation by greedy gives (1-1/e) (Nemhauser, Wolsey, Fisher, Math. Programming 1978); applied to summarisation by Lin & Bilmes, ACL 2011 ("A class of submodular functions for document summarization"); MMR (Carbonell & Goldstein, SIGIR 1998). Application to this task is design reasoning.
Why: "judged for truth and originality" and only the first 1,000 are scored. Redundant claims (same fact in 5 wordings) likely count as one idea or are penalised as non-original.
Objective: F(S) = sum_c P_c + lambda * [ #distinct subjects + #distinct (subject,attribute) + #distinct kinds + #distinct type-subtype (gt/lt/eq, up/down, relation link) ] with coverage terms concave (sqrt) so each new key adds less after the first; hard constraint on exact-text uniqueness and a per-key cap (<= 3 claims over all types per (subject, attribute)).
Recipe: greedy with lazy evaluation (priority queue), O(N log N); pool of 5-20k candidates is trivial.
Pitfalls: over-diversifying into low-P long-tail keys lowers truth; so impose floor P >= cutoff first, diversity second.
What would NOT help: clustering on text embeddings (all templates look alike but diversity is about content); random shuffling for diversity.

### Rank 4: Margin-based "safe inference" derivations (value algebra on timelines)
What: derive claims whose truth is robust to uncertainty in the underlying observations - compare with big gaps, change with earliest/latest clusters, at_event with bracketing, relation on constant facts, `fact` on keys with multi-year stability. This is not an independent algorithm so much as the way to use Rank 1-2; listed separately because it decides which candidates are safe.
Design reasoning; related idea: interval arithmetic / robust optimisation.
Expected gain: pushes compare/change from ~85% to ~97% true; these types are the most error-prone because they combine two uncertain values.
Rules of thumb: compare gt/lt requires min over plausible values (current cluster and the alternative cluster, if any) of a ordering unchanged; relative gap >= 10% for counts, any gap for dates >= 7 days; change requires both clusters weight>=2; fact requires P>=0.95.

## 2. How to choose which claims to generate (maximising truth)

1. Use only keys with a single dominant value cluster at the end: weight(current) >= 2 independent observations (distinct pages, >=7 days apart) or one gold (labelled-true) row, and no conflicting later observation.
2. Prefer gold-form facts from practice rows labelled true (no parser noise), then parsed rows agreeing with gold, then parsed-only (needs 3+ agreeing).
3. Exclude: approximations/ranges/comparison-valued rows (`over 10,000`: the value is `gt`, not an exact value; never turn it into a fact), op-valued gold forms (`max_upload_size ... op le`), booleans with a parsed negation unless two agree, plain 4-digit counts, anything with lie signals (row labelled false).
4. Estimated P(true) per type: fact = P_cur; compare = P_left x P_right x P(order stable) ~ product (assume independence; this is why compare is riskiest); change = P_fromcluster x P_tocluster (ordering of clusters is near certain if dated); at_event = P_val(at d) x P_event_date; relation = P_link x P_target_value x 1.
5. Final cutoff: choose the cutoff so the expected number of false claims in 1,000 is below ~25 (sum of 1-P).
6. Practice rows give a direct test of the entire pipeline: simulate "as-of" at an earlier date (e.g. 2026-08-15), generate claims from rows before it, and score them against later gold rows. That turns the calibration into a backtest and also catches template bugs.

Conservative vs ambitious: unknown scoring rule. Two probable forms: (a) score = sum over valid true claims of weight with a penalty for false (truth rate) plus an originality credit; (b) calibration reward on confidence. A robust mix: 100% claims with P >= 0.9; ~45% fact, 20% change, 15% compare, 10% relation, 10% at_event (see 5), and no ambitious low-P ones, because an invalid or false claim costs a slot (a lost 1/1000) and probably more (truth penalty), while an ambitious claim (e.g. eq compare or a rare relation) only adds originality credit if true. Use ambition ONLY along the dimensions that are free of truth risk: variety of type, attribute, phrase and value-kind. Confidence: calibrated P, never above 0.98 (cap), never below 0.5; do not set all 0.9 (a flat value gets no calibration credit under any proper scoring rule).

## 3. The referee's rules and hidden gotchas (all from the contracts) with how to avoid each

3.1 Names and aliases
- A name inside a longer entity's name names that one only: `Hooly AI Pro` is the plan, not Hooly. Also: `Hooly AI` is an alias of Hooly itself, but `Hooly AI Free/Pro` are separate subjects. `Hooly Android 16/17` vs `Hooly Android`, `Hooly Photos Plus/Lite/Max` vs `Hooly Photos`, `Hooly Pixel 10 Pro` vs `Hooly Pixel 10`, `Hooly Workspace Enterprise` vs `Hooly Workspace`, `Hooly Cloud Next 2026` vs `Hooly Cloud`, `Hooly I/O 2026` / alias `Hooly I/O`. Always write the canonical full name; never write a name followed by a word that extends it ("Hooly Cloud Next" is an alias of the event, so a Hooly Cloud fact must not be written "Hooly Cloud Next..."). Run a longest-match tokenizer in your validator and require exactly the expected subject(s) and event to resolve, and NO other subject resolves in the sentence (extra subject mentions can make "another name of same type" or compare ambiguity). Watch one-word aliases appearing in prose: `Search`, `Maps`, `Photos`, `Chrome`, `Android`, `Gemini`, `Translate`, `Vault`, `Jules`, `Meridian`, `Brightline`. Do not use "search", "maps" etc. as ordinary words in templates ("search" as verb); the referee is case-insensitive and whole-word.
- Avoid the alias `Hooly Inc.` (contains `.`, which does not end a sentence only for listed abbreviations; `Inc.` is listed but avoid) and avoid possessive `'s` mismatches: "Hooly's CEO" names Hooly (ok).
- `Hooly I/O 2026` contains `/`: fine as an exact phrase. `The May 2026 outage` is a subject whose name has a month and a year: they are inside the name and do not count, but do not rewrite it (e.g. "the outage in May").

3.2 One value, one date, no extra words (fact, at_event, relation)
- The sentence states the claim's value and no other value "of its kind, however written": no second price of the same currency+period, no second count of the same noun, no second amount in convertible units (a GB value and an MB value), no second percentage, version or date. A subject name containing numbers (`Hooly Android 16`, `Pixel 10`) is exempt only when it is the name the form needs; adding another entity ("replaces Hooly Android 16") is not.
- No date of its own unless it is the value: not "In 2026", "this year", "in April" (month even without a year), nor seasons, weekdays. "may" lower-case is not a month; avoid anyway.
- Time words banned in fact/at_event/relation sentences: ago, yesterday, tomorrow, once, formerly, previously, originally, initially, recently, lately, soon, eventually, then, before, after, since, until, till, earlier, later, used to, last/next week/month/quarter/year, in the past/future, at the time, at that time. Practical consequences: do not use "now", "currently" is not listed but avoid; do not use "since" in "open since November 2025"; attribute names `chair_since`, `soc2_audit_start`, `previous_employer` (contains "previous...", only "previously" is listed but avoid) must never be rendered with their words. `at the time of` is allowed ONLY as the at_event phrase. `launched`, `opened`, `released` are not time words: use these verbs with explicit dates ("Hooly Cloud launched in November 2025" - careful: that is a date value `2025-11` and must be the only date).
- The claim is judged on the date its type gives (fact: 29 Oct 2026; at_event: event date; relation: link period) so the sentence must not give another date; present tense is fine.

3.3 Negation
- Negation words anywhere in a form-holding sentence invalidate it: not, no, never, none, nobody, nothing, neither, nor, without, cannot, any word ending `n't`. EXCEPT for a yes-or-no claim, where the negation IS the polarity. Includes innocuous prose: "Hooly has no ..." in a true-value sentence. Also words like "nothing", "without" - ban them from all templates (compare, change, fact). "not only" etc. no.
- Value after a negation in its clause reads as nothing; a clause ends at `. , ; : ! ? . | blank line`. For polarity-no claims: the whole sentence (or each side of change) contains the negation and the attribute's words contiguous.

3.4 Yes or no (booleans: 174 gold facts, 90ish keys)
- The sentence must contain the attribute's words word-for-word contiguous, any case, with space, hyphen or nothing between words and between letters and digits: `soc2_certified` -> "SOC 2 certified"/"SOC2-certified"; `had_major_outage` -> "had major outage" (NOT "had a major outage"); `is_engineering_hub` -> "is engineering hub"; `end_to_end_encrypted_backups`; `raviqa_seat`; `integration_partner_of_flawless`; `replay_available`; `generally_available`. So grammatical English often fails: render booleans in a "tag" style: "Hooly Berlin Office: is engineering hub, yes." Not natural but safe? Careful: a yes does not contain a negation word, "yes" is fine. Recommended templates: yes: "{S} has {attr words}." only if words fit; otherwise "For {S}, {attr words} holds." ; no: "For {S}, {attr words} is not the case." Use "is not the case" only if the attr words contiguous. Validate with the round-trip.
- true claims with value false (polarity no) are valid and informative (the practice has such rows: "Hooly Chrome does not include an AI sidebar yet" - "yet" is not listed but avoid). Prefer yes polarity? A no-fact is still true. Keep a few; they give variety.
- Combined risk: `Hooly is not fully remote` (fully_remote): words "fully remote" present: good. `Hooly has never been SOC2-certified` is the documented example.

3.5 Money
- Must carry the period exactly as the form: monthly `€59 per month` (also `/month`, `a month`, `monthly`); one-off has NO period; a monthly price does not state a one-off price and vice versa. `per user per month` reads monthly. `from €39/month` is ok but "from" in a change sentence is a phrase, avoid in facts. Annual price: `€590 per year` (or `a year`). `price_per_user` (Drive, Gmail): form carries `per: month`? (verify in the data; practice forms decide).
- Currency from the form (EUR default `€`, but check others). Do not write "5 pounds". Decimal comma only in prices; use decimal point `€49.99`. Big numbers: write `€12,000,000` or `€12M` with capital M; lower-case `m` is metres (`10m users` is not read). `k` fine: `10k`.
- Three digits after the only point is ambiguous (`1.500`): avoid; write `1,500`.

3.6 Quantities, units, nouns
- Counted noun = the form's `unit` in singular; text may use plural; the referee compares in singular, so irregular plurals are a risk: use the noun exactly as the surface form in practice rows (learn a unit -> surface noun map from practice: e.g. person<->people, company<->companies, ticket etc.). Up to two words may sit between number and noun ("12 paying customers"). Do not insert 3 words.
- A plain four-digit number 1900-2099 is a year: write `2,048 customers`, never `2048 customers` or `1950 devices`; also counts >= 10,000 with comma. Write numbers in digits with commas; avoid scales unless needed (`10k`, `1.2 million` read fine but a mismatch like `1.20 million` is ok too; prefer full digits).
- Units list is closed: B KB MB GB TB (powers of 1,000), mm cm m km in, g kg, mAh, Hz kHz MHz GHz, mW W kW. Write the symbol exactly (`GB`, `mAh`, `W`). `"` for inch only straight after number; `6.1-inch` reads. Plural forms of the unit words (inches, kilograms) are NOT listed: use symbols. `1 GB` equals `1,000 MB`: do not use two. `B` is byte so a stray "B" after a number (e.g. "5 B") is bytes.
- Decimal commas (`1,5 GB`) read as nothing. Fractions in words (`half an hour`) do not read.
- Rates: "a day" after a count is a rate, not a duration. `daily_requests` (e.g. "20 requests a day") is a count of requests (unit request); the text "20 requests a day" works in practice rows - but if the value is the duration 1 day it would mislead; follow the practice surface exactly.
- Quantity gold forms with `op` (le/ge/gt/lt) are NOT exact values: never emit them as fact values (schema: `fact-with-op` is bad). Skip those keys for fact/change/at_event or find an exact-valued observation.

3.7 Dates
- Needs the year; precision as written: `12 March 2026` states a day, `March 2026` a month, `2025` a year. A form with `2026-06` must be written `June 2026`; a form `2026-06-09` as `9 June 2026` or ISO. Never numeric `12/03/2026` or `12.03.2026`; never `Q4 2026`; never "March 12". Months may be abbreviated; keep full names. Use ISO `2026-06-09` as the safest (single token).
- Fact sentences with a date VALUE have exactly one date: the value. No "on", "the 9th of" quirks needed. In relation the example is "joined on 1 July 2026".
- Date value inside a name is exempt only for the form's names (`Hooly I/O 2026`, `The May 2026 outage`, `Hooly Q1 2026 Results`, `Made by Hooly 2026`).
- Date-valued compare: phrases `after / later than`, `before / earlier than`, `on the same day as / the same day as`; but `before`, `after`, `later`, `earlier` are time words that the compare sentence may only use as the phrase itself, and not between amounts. For amounts these words are banned.
- Date precision problem: `2026-06` (month precision) vs a day date cannot be compared safely; only use date facts that have stable day-precision values.

3.8 Versions
- Forms: `v2.3`, `version 2.3`, `2.3.1`, or a capitalised name directly followed by x.y: `Hooly Gemini 2.2` (name part of value). Danger: the text "Hooly Gemini 2.2" reads as a version; and "Hooly Gemini" followed by decimal in other contexts accidentally becomes a version. Safe: "{S} runs version 2.3." Whole-number versions need `v3`/`version 3` (a bare "Hooly Gemini 11" is nothing). Compare versions as written (`2.3` != `2.3.0`).

3.9 Percent, durations
- `99.9%` (no space issue either way), `50 percent`. Three decimals allowed. Another percent in the sentence invalidates.
- Duration: unit kept as written and converts; months and years convert to each other (12 months = 1 year) but not to days. `a`/`an` as one only after under/within/in/for/over/than/at least/at most/to/only/just/about/around: avoid, write `1 week`. `30 days` is not 1 month. Use the unit of the form ("14 days", "52 min", "24h" ok).

3.10 Compare
- Sentence = left name, then ONE op phrase, then right name, in this order; the left subject first. NO numbers (`one`, `a dozen`, `hundred`), no month/season/weekday words, no time words (before/after only as the date phrase, never between amounts), no negation, no second op phrase.
- Phrase lists: gt `more … than | higher … than | greater … than | larger … than | bigger … than | longer … than`; lt `less … than | fewer … than | lower … than | smaller … than | shorter … than | cheaper … than`; eq `the same … as | as much … as | as many … as | as long as | as high as | equal to`. Gap `…` up to three words ("more paying customers than"). Natural sentences: "Hooly Workspace costs more than Hooly AI Pro." ; "Hooly Docs has more active users than Hooly Sheets." ; "Hooly Gemini supports more languages than Hooly Docs." Check that the gap words are not numbers or time words, and avoid mentioning a unit like "GB".
- Gotchas: (1) `Hooly Workspace costs more than Hooly.` -> Hooly names the company; always use the plan names. (2) `Hooly Workspace costs more than its rivals`: right subject not named. (3) Do not write "more expensive": `more expensive than` fits `more … than`? gap word is `expensive` (1 word): yes (documented). (4) same subject both sides: allowed with different attributes ("Hooly Cloud's standard storage costs more than Hooly Cloud's cool storage") but the form must carry different attributes; beware "neither does a fact with itself". (5) kinds must match: money same currency+period; quantities same counted noun or convertible units; dates vs dates; names and booleans never. (6) The ">=" ops are invalid (`op-ge` bad example): only gt, lt, eq. (7) `eq` is risky on rounding: values equal exactly after conversion only. (8) "cheaper" only for lt on prices makes sense; the referee does not check semantics, but a judge on originality may. (9) Compare is evaluated on values at 29 Oct, using each fact's value on that date ("on the day a value changes it holds the new one").
- Sentences before/after can be anything, so you may add an extra sentence for human readability, but it must also not break "originality" (not a copy). Not needed.

3.11 Change
- `from X to Y` (optionally `went up from` / `went down from`), or `Y, up from X`, `Y, down from X`. Each side must be a complete written value: `from €49 to €59 per month` is wrong (€49 has no period). Write `from €49 per month to €59 per month`. `up` requires to > from, `down` requires to < from; wrong direction invalidates. Names and booleans have no order: use plain `from ... to ...` without up/down. Booleans need the attribute words and the polarity of each side (`from not X to X`) - hard; skip booleans for change.
- The sentence may state when: "in April" allowed for change only, though add nothing (risk-free to omit).
- Subject must be named in that sentence (the plan itself, not a pronoun).
- "later date": non-adjacent pairs OK. The as-of date plays no part. 
- No negation, no extra phrase like "never went".

3.12 At event
- Phrases: `at`, `during`, `on the day of`, `at the time of` immediately before the event name (optionally "the" between). Event names/aliases from lexicon events; the event date is the event's date fact (some events lack a date fact: Employee Survey, Q results use `published`/other? in the lexicon the 13 events have attributes: date for 9/13; Q1-Q3 results and Sustainability Report may not have `date`: check, only date-attribute events). 7/13 events have a date fact in practice; in the full set more.
- Sentence must have only the one value; the event's year is inside its name and exempt. Time word `at the time` is the phrase's own.
- The subject must differ from the event, and not be alias-collide (e.g. subject `Hooly Cloud` vs event `Hooly Cloud Next 2026`: longer name wins, ok).
- Truth: the fact's value on the event date; use facts constant across the event date.

3.13 Relation
- Text holds: the link subject's name + the link attribute's words contiguous + the value; target is NOT named. Documented: "The CTO of Hooly joined on 1 July 2026." Words must be the link attribute's words: `CEO`, `CTO`, `head of product`, `Series A lead`, `headquarters`, `primary region`, `cloud provider`, `lead`, `city`; `chief technology officer` is NOT read. The link's attribute may be multi-word `head of workspace`, `head of security`, `series a co investor` (check lexicon spelling: `series_a_co_investor` reads "series a co investor"): a text like "Hooly's head of security joined on ..." is OK; "the Series A co-investor" -> hyphen between words is allowed ("co-investor" maybe "co investor": allowed: space, hyphen or nothing).
- Value date: "joined on 12 January 2026" (ISO also fine). Another date, "who left on ...", a time word ("after") banned.
- Name-valued relation attribute (`previous_employer`): the value Nimbus Cloud etc. Names: "no other entity of the same type": do not add other lexicon names. Verb phrasing: avoid "previous"/"previously"; e.g. "The CTO of Hooly came from X" - verify referee does not need attribute words for non-boolean (the doc says attribute words only matter for yes/no): it does not.
- True while the link named the target: the link's period (when the CTO was Gilfoil) must overlap with the constant fact. Use links whose target is the single value of the link throughout the observed window, or whose target changed (use both targets only if each link period is certain).

3.14 Sentences and format
- One sentence ending with `.`; avoid `e.g.`, `vs.`, `Inc.`; a decimal number like 99.9 is fine (no space after the point). Max 300 chars. Do not put `?` or `!`. A single line break inside a sentence is a space; avoid. CSV: use the csv module (commas, quotes). `form` is JSON text in the cell. `label` = `true`; `confidence` 0.5..1; `tag` is the schema field name but the CSV column is `label`. id unique, <= 64 chars `[A-Za-z0-9_.-]`.
- No zero-width/soft hyphen characters; use ASCII plus `€`; avoid NBSP.
- `form` for a name value: `{"kind":"name","value":"Bertram Gilfoil"}`; for fact the subject is the lexicon name (or alias); attribute exactly as lexicon writes it (lower-case underscores). Subject with no such attribute -> invalid. Compare form: `left/right` objects `{subject, attribute}`, `op`. At_event: `event` a STRING name (not citation). Relation: subject, link, target, attribute, value. No `op` in values; do not add extra fields (additionalProperties on entries is false; value objects have extra=false in claimed_value schema).
- Do not use the schema's `tag` as a CSV column.

3.15 Originality
- Text must not be a row of the input after lowercase / whitespace / trailing punctuation normalisation (check against all universe rows at run time, not just practice). Since sentences in the input are narrative ("Holdan started at Hooly on 12 January 2026."), template sentences coinciding is plausible for short fact templates: dedupe vs the full universe set with the same normaliser; on collision switch template variant (a second wording with different lead words). Likely "original" to a judge = not a copy of an input sentence and also semantically new (not the same fact restated in the input). Our best defence: more compare/change/at_event/relation claims, which almost never appear verbatim in the input, and facts on keys with few mentions.

## 4. Template/grammar design (always passes)

- Realiser = per-kind value writer (money, quantity, percent, date, duration, version, name, boolean) + per-(type) sentence skeletons + per-attribute "head" phrase table. Skeletons must contain only whitelisted words; maintain a banned word set (time words, negations, month/season/weekday names, numbers in words for compare, aliases of other subjects) and unit-test every output against it.
- Attribute phrase table: 62 subjects x ~10 attributes = ~600 (subject, attribute) pairs; write an attribute-class table (e.g. price -> "{S} costs {V}", count of users -> "{S} has {V}", date launched -> "{S} launched in {V}", duration -> "{S} lasts {V}"), then a handful of per-attribute overrides. Build the table semi-automatically: take practice rows with gold forms, cut the value span from the text, and use the surrounding words as the head phrase (the corpus supplies natural phrasing with the correct noun forms and units!). Then keep only phrases that pass the validator. This is a nearest-neighbour template induction: a "delexicalised" training sentence = text with the value and subject replaced by slots. It gives surface variety without an LLM. Filter out phrases containing time words, other values, negations, pronouns that refer to another sentence, and alias words of other subjects.
- Surface variety knobs that are safe: sentence order (value first: "At €59 per month, Hooly AI Pro..." is documented as valid), verbs (costs/is priced at), fact ordering in compare (swap sides + inverse op: gt <-> lt of swapped), synonyms in op lists (more/higher/greater/larger/bigger/longer for gt; less/fewer/lower/smaller/shorter/cheaper for lt), change forms (3 forms + up/down), at_event 4 phrases x event aliases (`Hooly I/O` vs `Hooly I/O 2026`), relation synonyms for link words: none (words fixed) but sentence frames vary ("The CTO of Hooly joined on ..." / "Hooly's CTO started on ..." / "Hooly's CTO joined Hooly on" -> fine if `Hooly` named).
- Do not vary into pronouns or anaphora; every sentence names its subject(s).

Estimated supply (to be recomputed on the full data): fact: hundreds to thousands (every stable key); compare: 70 shared numeric attrs on practice -> ~500 ordered pairs at gap >= 15%; change: 252 changing keys -> 252 x ~2 pairs; at_event: 7 events x ~10 stable keys; relation: 28 targets x 1-3 attributes -> ~40-80. Suggested target: fact 380 (including ~40 boolean polarity-no and ~60 date/name), compare 220, change 230, at_event 90, relation 60 (take whatever supply allows; fill the remainder with top-P facts). Per-key cap 3, per-subject cap 40.

## 6. Own-referee validator design (implement this first; ~1.5 h)

Parse and check, for each (type, form, text):
1. schema: jsonschema against entry.schema.json and claimed_value.schema.json (exact fields, no op, no extra); id regex; text length <= 300; label `true`; confidence in [0.5,1].
2. segmentation: split into sentences with the documented abbreviation exceptions; identify the sentence that holds the form (the one with the subject/value).
3. name resolution: longest-match, whole word, case-insensitive, spaces optional between words (value-forms: "with or without spaces"), over lexicon names + aliases; per-type required names found, extra names flagged.
4. value reader: implement value-forms for the 8 kinds (including approximations, negation-before-value, range, comparison words, decimal commas, scales, year-vs-count). Require: read values of the claim's kind in the sentence == exactly {claim value}, with no other value of the same kind (by currency+period / noun / convertible unit / date / version / percent).
5. type rules: fact (no date/time/month words, no other value; negation only for polarity, boolean attribute words); compare (op phrase from table, name order, no digits/number words/dates/time words/second phrase); change (phrase forms, up/down direction, each side's full value); at_event (phrase right before event name); relation (link words, no target name needed).
6. Round-trip metric: run it on the 1,581 true practice rows to measure false-rejects (our validator should accept their forms' value readings) - this checks our value reader vs the gold. Then on the generated claims it must pass 100%.
7. Mutation tests: for each generated claim apply "bad" mutations (add a time word, drop the period, add `over`, swap compare sides, swap up/down) and assert rejection. This documents each documented table row as a unit test (the contracts say every example is a test; copy them all).
8. Truth self-consistency: re-derive truth from the fact base for each claim by an independent code path (a different function) - fact value at 29 Oct; compare via values; change via two clusters; at_event via event date; relation via link period. Reject disagreement.
Pitfall: the value reader will be your parser's twin; reuse the team's parser only for the READ direction in the validator if it is robust; otherwise write a strict, small one (strictness is the point: when in doubt, reject).

## 7. Pitfalls specific to this data

- Gold forms exist only for practice; unlabelled rows come from your parser at precision ~0.91: do not use unlabelled-only keys for compare/change; fine for facts if 3+ agreement.
- Multi-fact rows: a true row's EVERY fact is true; a false row has at least one false fact. So practice false rows give no gold falsehood per fact.
- Pages dated 2025-10..2026-10 but the truth at 29 Oct includes future-scheduled things already past (events dated June/Sept): their attendance numbers appear only after the event.
- Fact values with op (le/ge) are common for limits: skip.
- `unsure` rows (39): exclude their facts.
- Do not rely on fact values from pages marked as quoting others/"rumour" patterns (the data has hype/lying pages); keep agreement-based.
- The run-time system must be deterministic and fit 2 CPUs/6 GiB/30 min: all above is a few seconds of Python; precompute the practice-derived phrase table into the image; write to /output/tmp then rename to output.csv; exactly 1000 claims (pad with the best remaining valid ones; never fewer, never more); ids unique.

## 8. Known work and applicability (honest assessment)

- TabFact (Chen et al. 2020), LogicNLG (Chen et al. 2020), FEVEROUS (Aly et al. 2021), ToTTo (Parikh et al. 2020): useful for the typology of logical claims (compare/count/superlative/temporal) and for the idea of generating claims from logical forms; their text generation is crowd-sourced or neural, not applicable under "no LLM at run time" and with a strict phrase-list referee. Use the typology only (design reasoning), not the models.
- Template-based NLG (Reiter & Dale 2000): applicable - indeed what the referee describes (controlled language).
- Table/KB question generation (e.g. WebQuestions/SimpleQuestions-style template induction): same idea as the delexicalised phrase table in section 4.
- Not helpful here: LLM paraphrase at dev-time for variety (output would leave the phrase lists; at most use LLM at dev time to propose the attribute-phrase table, then freeze and validate); neural fact verification models (our truth comes from the fact base); aggregate/superlative claims (rank, count of items) - `rank` is an invalid type (bad example) and no form exists.
