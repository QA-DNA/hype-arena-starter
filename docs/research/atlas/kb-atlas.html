TLDR

  1. Rules alone lose to "always true". On practice, always-true scores 0.833. Every rule system tried (exact vote, latest anchor, time-decayed votes, page reliability, intervals, blame) lands between 0.66 and 0.75 (measured, page-held-out). Rules catch over 90% of the false rows but call about a quarter of the true rows false. The reason is that the first page stating a real change looks exactly like a lie: 150 true single-fact rows state a new value that only a later page confirms.
  2. The biggest lever is a learned per-fact model over "bracket" evidence. Features say whether the fact matches the nearest anchor before its date, on the same day and after it, plus gaps, stale and premature flags and votes. Logistic regression scores each fact, a row's P(true) is the product over its facts, and isotonic calibration finishes it. Measured: 0.90 to 0.91 accuracy, false precision 0.76 to 0.79, Brier 0.073 (R80; optimistic, because the features were designed after seeing R80 errors).
  3. Calibration works and is cheap. Isotonic fitted on leave-one-page-out scores cuts ECE from about 0.16 to 0.04 on every rule and model. This is the 15% self-evaluation criterion, nearly for free.
  4. Truth discovery (page reliability EM) measured no gain, even though lies cluster on pages (186 of 277 false rows sit on pages with two or more). The harness cannot reproduce the real run's 10x unlabelled votes, so keep page reliability as a feature rather than the decider.
  5. Unsure is not predictable from evidence. The 39 unsure rows match anchors as often as true rows do. Emit unsure only where no evidence exists, and for every other row give the calibrated true or false.
  6. As-of values are the weakest KB answer. If you hide the last 20% of dates, the latest earlier anchor equals the final value for only 53% of keys. Every as-of answer must carry its P(true) and its support (pages, anchors); how the generator uses that is in claim generation.
  7. Stack: plain Rust, no engines. The full stack is a typed value enum with intervals, a HashMap timeline index, about 150 lines of features, logistic regression (linfa-logistic or about 60 lines of hand-written code), about 50 lines of PAV, and a witness list per verdict. No crate exists for truth discovery or calibration. Every database and logic engine studied was rejected, for a stated reason.

Build order, each step measurable on the harness before the next:

  1. Value semantics (S4). Val with to_interval(), the unit table and alias resolution, unit-tested with every example in contracts/value-forms.md. Insanity 1.
  2. Timeline index (S1). One Vec<Obs> per key, sorted, with labelled anchors marked. Insanity 1.
  3. Bracket features (S2, S3). Port the features from labs/kb-experiments/v9.py. Check that the Rust output matches the Python output on practice row by row. Insanity 2.
  4. Fact model and calibration (S6). Train logistic regression and isotonic offline on all practice rows with page-grouped out-of-fold features, then ship the coefficients and the PAV table in the image. Runtime does only arithmetic. Insanity 2.
  5. Generator interface (S7). The five queries over the timeline index and the fact model, each returning a value with P(true), its support and its witnesses. Unit-test each on practice keys with known changes. Candidate rules, selection and the self-check belong to the generator (claim generation). Insanity 1.
  6. Witness lists (S8) recorded at every step above, serialised for the UI. Insanity 1.
  7. Upgrades, only if the numbers move: per-key HMM or segmentation DP, Venn-Abers for the unsure band, page-liar latent state, conformal selection as the FDR statement.

Expected quality to state to the jury: about 0.90 accuracy with ECE about 0.04 where the row's key is covered by practice anchors (R80 regime, optimistic by an unknown margin), and about 0.85 or less on keys with no practice anchor (R10 stress regime). Confirm both on a holdout the features were not designed on before quoting them.

Measured on practice

Harness: labs/kb-experiments/ (exp.py for V0 to V8, v9.py for V9 to V11, results files next to them). The input is the practice form column. Pages are inferred as runs of consecutive ids sharing a date (291 pages, median 7 rows). Hidden pages lose their labels but keep their facts as votes, and a row's own page never counts as evidence for it.

  • R80: 5-fold GroupKFold by page, 80% of pages labelled. Anchor coverage per key is close to the real run, where every practice row is an anchor.
  • R10: 10 seeded splits with 10% of pages labelled (about 190 rows). This is a stress test for keys or subjects with no practice anchors, and the training set is tiny.

Facts verified with all labels visible:

  • All 202 single-fact false rows have their key stated on a true row of another page. 276 of 277 false rows have a fact that differs from some true anchor elsewhere, and 250 are contradicted by the latest true anchor at or before their date.
  • Single-fact rows by match with the nearest anchor before / same day / after (Y match, N mismatch, - no anchor on that side): Y-Y 275 true / 0 false · N-Y (new value, confirmed later) 150 / 18 · Y-N 130 / 23 · N-N 30 / 68 · no other anchor 79 / 0 (+7 unsure).
  • 33 of 39 unsure rows have every key stated elsewhere; "no evidence" explains none of them.
  • As-of test (labels hidden after 2026-09-03): the latest earlier anchor equals the final true value for 53.4% of keys at 75.5% coverage. Adding votes gives 50.8% at 79.4%.

Leakage, stated plainly: the shared kernel settings for V4 to V8 were fixed after seeing V3 R80 numbers, and the V9/V11 features were designed after reading R80 error examples. Treat V9/V11 as optimistic. Everything else (tau, window, thresholds, LR regularisation, isotonic fits) was chosen on labelled pages only. The next check is a holdout these features never saw, for example the forward-time split or the official every-fifth-row split.

Failure modes still open:

  • When a value changed is not observable between two bracketing anchors. Example: p-499, 80 templates on 05-20 with anchors 30 (03-20) and 80 (08-25), is false. The same pattern is true for 150 other rows.
  • Later restatements of an earlier figure. p-466 and p-455 restate Q1 2026 numbers on 10-27 and are true. The magnitude feature calls them false at confidence 1.00. This needs event-scoped values, for example "Q1 2026 customers".
  • Easy misses the learner still makes. p-365 is predicted true at 0.81 although mismatching anchors sit on both sides, so a hard rule on N-N patterns should override the model.

Contract details that change the KB design

These come from contracts/ and override generic advice found in the literature (two research reports suggested the opposite and were corrected):

  • Values are exact. over 100 customers is gt 100, about 100 reads as nothing, and there is no rounding tolerance: do not treat 1.2 million as a range.
  • Data units are powers of 1,000 (1 GB states 1,000 MB). Months and years never convert to days.
  • Versions compare as written: 2.3 is not 2.3.0. Do not normalise with semver.
  • Money compares only within one currency and one period; a monthly price does not state a one-off price. Treat a different period as a different value kind, not a contradiction.
  • Names resolve through every name and alias in lexicon.json; a name inside a longer name names the longer one only (Hooly AI Pro is not Hooly).
  • On the day a value changes, it already holds the new one (claim-forms, Compare section).
  • unsure carries no confidence; an unlabelled row with no output row counts as unsure.

Risks and open questions

  • The label scoring metric is not published. The unsure threshold trades coverage for precision without knowing the exchange rate. Report the trade-off curve, pick one point, say why.
  • Practice has 80% of rows labelled in a 5-fold split, the real run about 10%. Numbers from the 10% regime are the ones to quote to the jury.
  • New subjects, attributes and events at evaluation: every prior must be derived from data (attribute behaviour, staleness) with a default for unseen attributes, never hardcoded.
  • The image may contain data/practice.csv, so the official checker's label count is an upper bound. Self-evaluation must come from page-held-out runs, not from scripts/check.sh.
  • The as-of answer rests on the last observations of each key; a lie on the last page of a key is the most dangerous case. value_at reports how many independent pages and anchors support the value, so the generator can require two.
